# ADR-0002: Synapse остаётся эталоном поведения

- Статус: принято; условия заимствования уточнены при переходе на AGPL
- Дата: 2026-11-17; изменено 2026-11-27

## Контекст

Проект — порт Synapse на Go. Спецификация Matrix описывает **что** должно происходить, но не покрывает
краевые случаи, порядок событий, тексты ошибок и де-факто поведение, на которое опираются клиенты.
Попытка «делать только по спеке» приводит к расхождениям с реальными клиентами и к спорам на ревью.

## Решение

1. **Synapse — постоянный референс.** Наш сервер обязан воспроизводить его поведение, включая краевые случаи.
2. **Спека — контракт и язык обсуждения**, Synapse — эталон реализации. Сначала формулируем поведение по спеке,
   затем сверяем с Synapse.
3. **При расхождении** по умолчанию делаем как Synapse (совместимость клиентов важнее «чистоты»), решение
   фиксируем в ADR с датой пересмотра.
4. **Код Synapse читаем** как источник истины по алгоритмам и форматам. Проект распространяется под
   `AGPL-3.0-or-later`, поэтому перенос и адаптация кода допускаются при сохранении copyright/AGPL
   уведомлений, указании upstream-файла и pin, даты модификации и записи в `NOTICE`. Архитектуру Go
   и Twisted/Python не смешиваем: адаптируем реализацию, а не механически переносим внутренние классы.
5. **Изменения Synapse отслеживаем** регулярной сверкой с его релизами и changelog спеки:
   по каждому пункту решение «переносим / не переносим (причина) / ждем».
6. **Проверка совместимости** — Complement с ratchet плюс точечные differential-тесты наш сервер ↔ Synapse
   на критичных сценариях (auth, membership, state resolution, `/sync`).

## Последствия

- Задачи формулируются как «поведение X как в Synapse, спека: раздел Y», а не «по спеке, потому что так правильно».
- Расхождение с Synapse — дефект, а не «улучшение», если не оформлено ADR.
- Появляется регулярная сверка с релизами Synapse; она дешевая, но обязательная.
- Подтверждённые производные файлы (`internal/state/state.go`, `synapse_diff_test.go`,
  `synapse_units_test.go`) сохраняют upstream copyright и AGPL-уведомления; реестр находится в `NOTICE`.

## Реестр расхождений «спека ↔ Synapse»

Пункт 3 (делаем как Synapse) применяется к конкретным местам; реестр ниже ведётся, чтобы такие решения
не «возвращали обратно» при следующем чтении спеки. Пересмотр — при смене мажорной версии Synapse.

| Дата | Место | Спека | Synapse 1.165.0 (эталон) | Решение |
|------|-------|-------|--------------------------|---------|
| 2026-11-20 | Redaction content: `m.room.guest_access` | Список защищённых ключей redaction включает `guest_access` (исторические версии комнат) | `prune_event` вырезает `guest_access` → при redaction content пустой | Как Synapse: `guest_access` вырезается. Сверено по `event_id` события из живого Synapse, а не по тексту спеки. |
| 2026-11-21 | Клиентские `GET /profile/{userId}` (и поля), `GET /directory/room/{alias}`, join по алиасу для чужого сервера, когда его `/query/*` не ответил | Описан только 404 (нет профиля/алиаса) | Сбой сети или 5xx чужого сервера - 502 (`Failed to fetch profile`, `Unable to fetch alias`) | Отклонение: 404 `M_NOT_FOUND`. На 502 Element показывает «Unknown server error» вместо штатного «may not exist» и не отправляет приглашение. Ответ и отказ кэшируются на 1 мин и 15 с. |

Проверка перед изменением redaction: сравнить `event_id`, посчитанный из pruned-события, с тем, что
отдаёт живой Synapse на том же событии. Текст спеки вторичен.
