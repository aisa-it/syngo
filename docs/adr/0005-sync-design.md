# ADR-0005. `/sync` как first-class SLO: модель, доступ к данным и правила производительности

- Статус: принято
- Дата: 2026-11-17
- Референс поведения: `element-hq/synapse` @ `40f63e0` (`synapse/handlers/sync.py`,
  `synapse/storage/databases/main/stream.py`, `synapse/storage/databases/main/state_deltas.py`),
  схема — `current_state_delta_stream`, `stream_ordering`.

## 1. Контекст и цель

По опыту Dendrite именно `/sync` убивает производительность на реальных аккаунтах: на пустой базе
всё быстро, на аккаунте с 500–1000 комнат появляются N+1 запросы и p99 уезжает в секунды.
Поэтому `/sync` проектируется **до** реализации остальных чтений, с зафиксированным SLO,
измеримым стендом и правилами доступа к данным, которые проверяются тестом, а не «на глаз».

Здесь фиксируются проектная модель, стенд и отчет. Реализация самого цикла - следующим шагом,
но ADR фиксирует контракт, чтобы код не разъехался с моделью.

## 2. Целевой SLO (предложение на согласование)

| Метрика | Цель | Как измеряем |
|---|---|---|
| p99 **incremental** `/sync` (пустой ответ, long-poll=0) | **≤ 150 мс** на профиле 500–1000 комнат | стенд `make bench-sync`, 10 конкурентных клиентов |
| p99 **incremental** `/sync` при 10 новых событиях в 10 разных комнатах | ≤ 250 мс | тот же стенд, сценарий `delta` |
| p99 **initial** `/sync` (1000 комнат, ≤20 событий на комнату) | ≤ 1.5 с | стенд, сценарий `initial` |
| Число SQL-запросов на один `/sync` | **не зависит от числа комнат** (константа ≤ 8) | счётчик pgx-трейсера в стенде |
| RSS процесса при профиле 1000 комнат / 10 клиентов | **≤ 50 % от Synapse** на том же профиле | замер стенда + замер Synapse (когда будет поднят) |
| Long-poll (timeout=30 c, событий нет) | не занимает БД-соединение в ожидании | проверка метрикой занятости пула |

Правило проверки: SLO мягкий (warning) в CI до стабилизации, жёсткий — после трёх недель зелёных прогонов.

## 3. Модель ответа

Формат — как в CS-API v1.11 `GET /_matrix/client/v3/sync`:

```
{
  "next_batch": "<opaque>",
  "rooms": {
    "join":  { "<room_id>": { "timeline": {"events": [...], "limited": bool, "prev_batch": "<opaque>"},
                              "state": {"events": [...]},
                              "ephemeral": {"events": [...]},
                              "account_data": {"events": [...]},
                              "unread_notifications": {...} } },
    "invite": { "<room_id>": {"invite_state": {"events": [...]}} },
    "leave":  { "<room_id>": {"timeline": {...}, "state": {...}} }
  },
  "presence": {"events": [...]},
  "account_data": {"events": [...]},
  "to_device": {"events": [...]},            // интерфейс, реализация — этап E2EE
  "device_lists": {"changed": [], "left": []}, // заглушка до E2EE
  "device_one_time_keys_count": {}             // заглушка до E2EE
}
```

Параметры запроса: `since` (токен), `timeout` (0–30000 мс), `full_state` (bool), `filter` (id или inline),
`set_presence`. Неизвестные параметры игнорируются (как в Synapse).

## 4. Токен `next_batch`

Токен — **opaque** для клиента, внутри: позиция глобального `stream_ordering` плюс версия формата.

```
v1.e<events_stream_ordering>
```

- Одно число достаточно: любое событие (обычное или state) увеличивает глобальный `stream_ordering`,
  поэтому «что нового после since» — это `events.stream_ordering > since`.
- Токен подписывается HMAC (server_name + секрет из конфига), чтобы клиент не мог подделать позицию
  и спровоцировать полный пересчёт (Synapse тоже использует непрозрачные токены).
- `prev_batch` для `timeline` — тот же формат, но с позицией события, с которого начинается порция.
- Дополнение: `v1.e<n>[.t<to-device>][.r<эфемерные>]`. `t` - закладка
  очереди to-device, `r` - версия потока typing и receipts (в памяти процесса, начинается с
  времени старта в микросекундах, поэтому токен до рестарта старше любой новой версии).
  Incremental sync с `r` отдает только join-комнаты с изменениями: события, состояние,
  typing/receipts новее `r`, room account data, новый вход; приглашение - один раз. Токены без
  `r` читаются как прежде (все комнаты).
- Счетчики `unread_notifications` - хранимые действия push-правил
  (`event_push_actions`, как в Synapse): события разбираются один раз по `stream_ordering`,
  счетчики - сводка `event_push_summary` на пользователя, комнату и тред: порция
  разбора увеличивает ее в той же транзакции, receipt и свое событие поднимают позицию прочтения
  и пересчитывают только строки выше нее, прочитанные строки удаляет фоновая чистка; `/sync`
  читает сводку одним запросом O(комнат).

## 5. Доступ к данным: константное число запросов

Ключевое правило: **никаких запросов «на комнату»**. Один `/sync` выполняет фиксированный набор
запросов независимо от того, 10 у пользователя комнат или 1000.

| # | Запрос | Что даёт |
|---|---|---|
| 1 | членства пользователя: `SELECT room_id, membership FROM room_memberships WHERE user_id=$1 AND ...` + `rooms` (одним JOIN) | список комнат и их membership для join/invite/leave |
| 2 | события с момента токена по списку комнат: `SELECT ... FROM events WHERE room_id = ANY($1) AND stream_ordering > $2 ORDER BY stream_ordering` | timeline (с лимитом на комнату и `limited`-флагом) |
| 3 | текущее состояние комнат, где были изменения: `SELECT ... FROM room_state WHERE room_id = ANY($1)` | `state.events` — снапшот, не дельта |
| 4 | account_data пользователя (`user_account_data` + `room_account_data`, таблицы появятся с account data) | account_data |
| 5 | (long-poll) ожидание нотифаера по `stream_ordering` — без БД | пустой ответ с тем же `next_batch` |
| 6 | (опционально) метаданные комнат для `unread_notifications` | счётчики |

Почему не дельта-стрим состояния (как `current_state_delta_stream` в Synapse): у нас state
материализован в `room_state` (ADR-0003), и комнат, где state менялся с прошлого sync, обычно единицы.
Снапшот `room_state` по `ANY($1)` для этих комнат — один запрос и всегда актуальное состояние,
без второй таблицы и без риска разъехаться. Если профилирование покажет, что при массовых
state-изменениях снапшот дороже дельты — добавим `current_state_delta_stream` отдельной миграцией
(таблица уже предусмотрена в ADR-0003 как возможное расширение).

## 6. Lazy-loading участников

- По умолчанию (без фильтра) отдаём `state` как в спеке.
- При `filter.lazy_load_members=true` в `state.events` включаем только:
  `m.room.member` отправителей событий из `timeline` этой порции + самого пользователя +
  тех, чьи membership-события изменились с `since`. Это даёт клиенту возможность отрисовать
  комнату без загрузки 1000 участников.
- Список нужных `user_id` собирается из уже полученных событий (без дополнительных запросов).

## 7. Long-polling

- `timeout` ограничен конфигом `sync.max_timeout` (по умолчанию 30 000 мс), отрицательный → 0.
- Ожидание — через нотифаер по глобальному `stream_ordering`: горутина ждёт `chan struct{}`, который
  закрывается при записи любого события, и перепроверяет позицию токена. **БД-соединение на время
  ожидания не удерживается** (иначе 10 висящих `/sync` съедят весь пул).
- Новое событие в чужой комнате → перепроверка (может быть не наша), поэтому ответ может быть пустым
  с тем же `next_batch` — это допустимо спекой.
- Отмена — по `r.Context()` (клиент закрыл соединение).

## 8. Нагрузочный стенд (`make bench-sync`)

- `cmd/syncload`: генератор данных (N пользователей × M комнат × K событий) пишет напрямую в схему
  через `store`, затем гоняет сценарии:
  - `initial`: 1 клиент, 1000 комнат, первичный `/sync`;
  - `empty`: 10 клиентов, `/sync` с актуальным токеном (long-poll=0) — самый частый случай;
  - `delta`: 10 клиентов, между вызовами пишется 10 событий в 10 разных комнат.
- Считает p50/p95/p99, RPS, число SQL-запросов на `/sync` (pgx `QueryTracer`), RSS процесса сервера
  (читается из `/proc/<pid>/status`), пишет отчёт `bench/sync-<профиль>.md`.
- Профиль и параметры — флагами, фиксируются в отчёте; один прогон = одна команда `make bench-sync`.
- Стенд работает и против внешнего сервера (`-base-url`), поэтому его можно навести на Synapse
  и получить сравнение для метрики «RSS ≤ 50 % от Synapse».

## 9. Что проверяет CI

- Юнит-тесты токена (`encode/decode`, подпись, несовпадение версии → `M_UNKNOWN_POS`).
- Тест «число запросов не растёт»: с 10 и 100 комнатами счётчик pgx-трейсера одинаков на `empty`-сценарии.
- Тест lazy-loading: в `state.events` только ожидаемые `m.room.member`.
- `make bench-sync` — мягкий прогон (warning) с публикацией отчёта артефактом.

## 10. Границы

- **В scope**: initial/incremental sync, токены, lazy-loading, long-polling, стенд, SLO, отчёт.
- **Вне scope**: to-device/E2EE-расширения (интерфейс-заглушка), presence/typing/receipts (отдельно),
  sliding sync (MSC4186 — не в v1.11), фильтры сверх `lazy_load_members`/лимитов, федерация.

## 11. Риски

| Риск | Ответ |
|---|---|
| Снапшот `room_state` дороже дельты при массовых state-изменениях | замер в стенде; при регрессии — `current_state_delta_stream` отдельной миграцией |
| Long-poll съедает пул соединений | ожидание через нотифаер без БД (см. §7) + метрика занятости пула в стенде |
| «Тихий» N+1 появится позже (например, профили участников) | тест-счётчик запросов в CI на сценарии `empty` и `delta` |
| SLO 150 мс окажется недостижим на нашем железе | SLO фиксируется по первому замеру + план улучшений, но не отменяется: иначе повторяем ошибку Dendrite |
