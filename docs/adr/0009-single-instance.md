# ADR-0009: один экземпляр syngod на базу, масштабирование - после выноса состояния

Дата: 20.11.2026. Статус: принято.

## Контекст

README заявлял горизонтальное масштабирование, но часть состояния живет в памяти процесса.
При двух экземплярах за балансировщиком на одной базе аудит кода нашел: потерю событий
в `/sync` (long-poll на втором экземпляре не будится), 401 на втором шаге регистрации
(UIA-сессия создана на другом экземпляре), дубли федеративных транзакций (пачку outbox
берут оба воркера).

Состояние в памяти процесса (на 20.11.2026):

| Состояние | Где | Что ломается при двух экземплярах | Путь выноса |
| --- | --- | --- | --- |
| Нотифаер long-poll `/sync` | `internal/api/sync.go` (`syncNotifier`) | событие с экземпляра A не будит ожидающих на B: ответ приходит только по таймауту | `LISTEN/NOTIFY` по каналу `syngo_stream` (позиция и user id) |
| Безопасная позиция `/sync` (незакоммиченные `stream_ordering`) | `internal/store/store.go` (`pending`) | B не знает о транзакциях A: `next_batch` может перескочить событие, которое закоммитится позже | позиция из БД: минимум из незакоммиченных по таблице выданных позиций или `pg_snapshot_xmin` |
| Typing, presence | `internal/core/ephemeral.go` | видны только клиентам того же экземпляра | `NOTIFY` + локальный кэш с TTL или таблица `UNLOGGED` |
| Receipts | `internal/core/ephemeral.go` (кэш), таблица `receipts` | кэш загружается при старте; запись на A не попадает в кэш B | чтение из БД или инвалидация через `NOTIFY` |
| UIA-сессии | `internal/core/uia.go` | второй шаг регистрации/смены пароля на другом экземпляре - 401 | таблица `uia_sessions` с TTL |
| Неудачные пароли в UIA | `internal/api/uia.go` (`uiaFails`) | лимит делится на число экземпляров | таблица или общий лимитер |
| Nonce регистрации общим секретом | `internal/api/shared_secret_register.go` | nonce с A не принимается на B | таблица с TTL |
| OpenID-токены | `internal/api/openid.go` | токен с A не проверяется на B | таблица с TTL |
| Rate limiter клиентов и федерации | `internal/ratelimit`, `internal/federation/transport` | лимит умножается на число экземпляров | счетчики в PostgreSQL (`UNLOGGED`) или лимит на балансировщике |
| Сериализация рассылки профиля, to-device по устройству | `internal/api/keyed_lock.go`, `syncLocks` | гонки между экземплярами | `pg_advisory_xact_lock(hashtext(key))` |
| Сериализация upgrade комнаты | `internal/core/room.go` (`upgradeMu`) | два upgrade одной комнаты параллельно | `pg_advisory_xact_lock` по room id |
| Очереди доставки push | `internal/pushers/delivery.go` | при рестарте недоставленное теряется; при двух - каждый шлет свои события, дублей нет, но и общей очереди нет | таблица очереди с `FOR UPDATE SKIP LOCKED` |
| Захват пачки outbox федерации | `internal/store/federation_queues.go` (`ClaimOutboxBatch`) | `SELECT` без блокировки: оба воркера шлют одну транзакцию | аренда пачки: `FOR UPDATE SKIP LOCKED` + `leased_until` |
| Медиа | локальный каталог `media.directory` | файл, загруженный на A, не виден B | общий том (NFS) или S3-хранилище (сейчас отклоняется валидацией) |

Вынести все это - отдельная работа по каждому пункту (схема, миграции, тесты на двух
экземплярах), включая e2e-прогон регистрации, `/sync` и федерации на двух процессах.
Частичный вынос (только `LISTEN/NOTIFY` для `/sync`) опаснее явного запрета: оператор
решит, что масштабирование работает, а регистрация и федерация будут ломаться.

## Решение

1. **Поддерживаемая топология - один процесс syngod на базу.** Масштабирование - вертикальное
   (CPU, `database.max_conns`), высокая доступность - быстрый перезапуск (systemd/compose
   `restart`) и восстановление из бэкапа (`docs/operations.md`). README больше не заявляет
   горизонтальное масштабирование.
2. **Защита от второго экземпляра** (реализовано):
   - при старте syngod берет сессионную advisory-блокировку PostgreSQL
     `pg_try_advisory_lock(0x53594e47, 1)` на отдельном соединении (не из пула) с
     `application_name = "syngod-instance host=<hostname> pid=<pid> id=<random>"`. Для меток длиннее
     63 байт или с символами вне печатного ASCII сохраняются читаемое начало и 96-битный хеш
     полной метки. В журнале старта видны обе формы;
   - если блокировку держит другой процесс, syngod ждет до 30 с (перекрытие при рестарте:
     старый процесс еще завершается) и падает с ошибкой, где указан держатель
     (`application_name`, адрес клиента, `backend_pid`, время старта соединения):
     `startup: store: database is already used by another syngod instance (...)`;
   - каждые 5 с соединение с блокировкой проверяется; при обрыве (рестарт PostgreSQL, сеть)
     блокировка берется заново; пока она не взята, `/health/ready` отвечает 503
     (`instance_lock`), метрика `syngo_instance_lock_held` = 0;
   - если за время обрыва базу занял другой экземпляр, процесс завершается с ошибкой
     `instance lock lost` (лучше упасть, чем работать вдвоем);
   - собственный зависший backend (соединение закрыто только на стороне клиента) узнается по
     `application_name` и завершается `pg_terminate_backend`.
3. **Миграции** (`syngo-migrate`) блокировку экземпляра не берут: у golang-migrate своя
   одноключевая advisory-блокировка; ключи не пересекаются.
4. **План масштабирования** (отдельными шагами, порядок - по ценности):
   1. позиция `/sync` из БД вместо `pending` в памяти и `LISTEN/NOTIFY` для нотифаера;
   2. UIA-сессии, nonce регистрации, OpenID-токены - в таблицы с TTL;
   3. аренда пачек outbox (`FOR UPDATE SKIP LOCKED`, `leased_until`) и очередь push в БД;
   4. advisory-блокировки транзакций вместо мьютексов (upgrade, профиль, to-device);
   5. общий лимитер (PostgreSQL или балансировщик), typing/presence через `NOTIFY`;
   6. общее хранилище медиа (S3);
   7. e2e-тест на двух экземплярах (регистрация, `/sync`, федерация); после него блокировка
      экземпляра заменяется ролями (несколько API-экземпляров, один воркер федерации и push
      по той же advisory-блокировке).

## Альтернативы

- **Сразу несколько экземпляров с `LISTEN/NOTIFY` только для `/sync`.** Закрывает одну из
  четырнадцати строк таблицы; регистрация, outbox и лимиты остаются сломанными. Отклонено.
- **Sticky-сессии на балансировщике.** Не помогает: события пишут разные пользователи на
  разных экземплярах, outbox-воркеры работают на всех. Отклонено.
- **Запрет только документацией.** Ошибку конфигурации (две реплики в compose/k8s) никто не
  заметит до потери событий. Отклонено: нужна техническая защита.
- **Блокировка через строку в таблице с heartbeat.** Требует миграции и выбора таймаута
  протухания; advisory-блокировка снимается сервером сама при обрыве соединения. Отклонено.
- **Redis/etcd для блокировки и состояния.** Новая зависимость в эксплуатации, бэкапе и
  мониторинге при том, что PostgreSQL уже дает `LISTEN/NOTIFY` и advisory-блокировки.
  Отклонено.

## Последствия

- Две реплики syngod на одной базе невозможны: вторая не стартует с понятной ошибкой.
  В Kubernetes - `replicas: 1` и стратегия `Recreate` (или `RollingUpdate` с `maxSurge: 0`).
- Простой при рестарте - время старта нового процесса (секунды); при переходе на
  несколько экземпляров - нулевой.
- Отдельное соединение с базой на процесс (в лимите `max_connections` учитывать
  `database.max_conns + 1`).
- Миграция схемы не нужна.
