# ADR-0008: собственный admin-контур (не Synapse-compatible)

Дата: 19.11.2026. Статус: предложен.

## Контекст

Admin API Synapse (`/_synapse/admin/v1/*`) не входит в спецификацию Matrix и является частным
интерфейсом Synapse. Нам нужен эксплуатационный контур: пользователи, комнаты, медиа, аудит.
Копировать формат Synapse целиком не обязательно и рискованно (внутренние идентификаторы,
разные форматы ошибок), но и ломать привычные инструменты не хочется.

`docs/api-scope.md` §4 фиксирует: «Admin API Synapse не входит в спеку; у нас будет собственный
admin-контур (отдельно)». Эта ADR — предложение по формату до реализации.

## Решение (предлагается)

1. **Префикс:** `/_syngo/admin/v1/*`. Не пересекается с `/_synapse/*` и Client-Server API,
   явно показывает, что контракт наш.
2. **Авторизация:** отдельный admin-токен, не пользовательский access token.
   - `users.is_admin` уже есть в схеме — используем его для выдачи admin-токена.
   - `POST /_syngo/admin/v1/login` с логином/паролем админа → `admin_token` (хранится как
     обычный access token с отдельным scope `admin`; TTL по конфигу, по умолчанию **12 ч**).
   - Все admin-эндпоинты требуют `Authorization: Bearer <admin_token>`; пользовательские токены
     отклоняются с 403, даже если `is_admin = true` (явное разделение контуров).
   - Отдельная секция конфига: `admin.enabled`, `admin.token_ttl` (по умолчанию **12 ч**, как в
     `config.Default()`), `admin.audit_retention`.
3. **Формат:** JSON, ошибки `{errcode, error}` как в CS-API (переиспользуем коды), списки —
   `{items: [...], total: N, next_token: "..."}` для пагинации.
4. **Минимальный набор (v1):**
   - пользователи: `GET /users`, `GET /users/{userId}`, `POST /users/{userId}/deactivate`,
     `POST /users/{userId}/password` (сброс), `POST /users/{userId}/admin` (выдать/снять роль);
   - комнаты: `GET /rooms`, `GET /rooms/{roomId}`, `POST /rooms/{roomId}/delete`,
     `POST /rooms/{roomId}/leave` (от имени сервера);
   - медиа: `GET /media`, `POST /media/{serverName}/{mediaId}/quarantine`,
     `DELETE /media/{serverName}/{mediaId}/quarantine`;
   - аудит: `GET /audit?since=&limit=`.
5. **Аудит:** таблица `admin_audit(id, actor, action, target, details jsonb, created_at)`.
   Пишутся все изменяющие операции (деактивация, сброс пароля, удаление комнаты, quarantine).
   Ретенция — по `admin.audit_retention`, чистка в воркере.
6. **Ограничения v1:** нет impersonation, нет удаления пользователей (только деактивация),
   нет федеративных операций. Это осознанно: опасные операции добавляем после аудита.

## Уточнения реализации

| Что | Как |
|---|---|
| Аудит | успешное изменяющее действие пишется в транзакции самого действия (без записи действие откатывается); отказ или ошибка - отдельной записью. `details.result`: `ok` / `denied` / `not_found` / `error`, при отказе `details.reason` (`last_admin`, `self`, `not_found`, ...). Пароли, hash и токены в аудит не пишутся. Пишутся также `login`, `logout` и регистрация через shared secret (`actor = shared_secret`) |
| Блокировка комнаты | `PUT /rooms/{roomId}/block {"block": bool}`, `GET /rooms/{roomId}/block` -> `{"block", "user_id"}` (как в Synapse); `DELETE /rooms/{roomId}` без purge - блокировка. В заблокированной комнате пользователям запрещены join, invite, события и состояние; разрешены выход, kick и ban. Блокировка не зависит от существования комнаты и переживает purge |
| Purge | `DELETE /rooms/{roomId}?purge=true[&block=true]`: tombstone и leave локальным участникам, затем одной транзакцией удаление комнаты и связанных строк (`event_auth`, `transactions`, `account_data`, `receipts`, `destination_rooms`, PDU в `federation_outbox`) и аудит |
| Последний админ | снятие роли и деактивация админа сериализуются advisory-блокировкой; на сервере всегда остается активный админ (`403 Cannot remove the last admin`) |
| admin-токен | `POST /logout` отзывает текущий admin-токен; снятие роли отзывает admin-токены цели; устройство `ADMIN` не видно в `/devices` пользователя |

## Альтернативы

- **Полная совместимость с `/_synapse/admin/v1`.** Плюс: готовые инструменты Synapse Admin UI.
  Минус: тащим чужой контракт и его исторические особенности, включая форматы, которые мы не
  хотим поддерживать. Отклонено: ADR-0001 — мы не обязаны сохранять admin-совместимость.
- **Admin через CS-API с флагом `is_admin`.** Минус: смешение ролей, повышенный риск утечки
  прав через пользовательские токены. Отклонено.

## Последствия

- Появляется отдельная поверхность атаки — включается только при `admin.enabled: true`.
- Нужны миграция `admin_audit`, роль `is_admin` в выдаче токенов и воркер ретенции.
- `docs/api-scope.md` §4 обновляется ссылкой на эту ADR.
- Реализация - отдельными изменениями: (1) аутентификация админа + аудит, (2) пользователи,
  (3) комнаты, (4) медиа.

## Открытые вопросы

- Формат `next_token`: непрозрачный base64 (как в `/sync`) или `offset`? Предлагаю непрозрачный.
- Нужен ли read-only admin-токен для мониторинга (только GET)? Предлагаю отдельный scope
  `admin:read` во втором срезе.
