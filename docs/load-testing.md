# Нагрузочное тестирование сервера

`cmd/syncload` меряет только слой /sync внутри процесса, без сети.
Этот документ - про нагрузку сервера целиком: запущенный syngod (или Synapse для
сравнения) под потоком клиентских запросов по HTTP, как от Element.

| Что | Где |
|---|---|
| Генератор нагрузки | `cmd/loadgen` |
| Стенд syngod | `scripts/load-stand.sh` (`make load-stand-up`) |
| Прогон | `scripts/load-run.sh` (`make load-smoke`, `make load PROFILE=M`) |
| Synapse для сравнения | `deploy/loadtest/docker-compose.synapse.yml`, `scripts/load-synapse.sh` |
| Отчеты | `var/loadtest/<время>-<профиль>-<сервер>/report.{json,md}` (не в git) |
| Эталонный smoke | `bench/load-smoke-S.{md,json}` (прод-конфиг), `bench/load-smoke-S-maxconns30.{md,json}` (пул БД 30) |

## 1. Цели

- Найти предел одного процесса syngod на прод-конфиге: при каком числе активных
  пользователей и частоте действий задержка доставки и ошибки выходят за SLO.
- Видеть, во что упирается сервер: CPU процесса, пул соединений БД, запросы PostgreSQL,
  лимиты (429), long-poll.
- Сравнивать с Synapse под тем же сценарием (тот же генератор, те же профили).
- Ловить регрессии между версиями: формат отчета постоянный (`report.json`, поле `format`).

## 2. Сценарий

Пул из `users` пользователей. Подготовка (в замер не входит):

1. Регистрация через `/_synapse/admin/v1/register` (`registration_shared_secret`, без UIA),
   открытую регистрацию (`-register open`, UIA `m.login.dummy`) или вход уже созданных
   (`-register login`). Токены кешируются в `var/loadtest/tokens.json` по адресу сервера:
   повторный прогон не плодит устройства; протухший токен (сброс базы) проверяется `/whoami`
   и пользователь заводится заново.
2. Ключи устройства (`device_keys`, 20 one-time keys) - один раз на устройство; фильтр /sync
   как у Element: `lazy_load_members`, `timeline.limit` 20, без presence.
3. `rooms` комнат профиля с алиасами `#<prefix>-room-NNNN` (повторный прогон переиспользует),
   `encrypted_rooms_percent` из них с `m.room.encryption`.
4. Членства: каждый пользователь в `rooms_per_user` комнатах, популярность комнат - закон
   Ципфа с показателем `room_skew` (1.0: одна-две «общие» комнаты почти со всеми и длинный
   хвост маленьких). Распределение детерминировано `seed`.

Нагрузка. Каждый активный пользователь держит long-poll `GET /sync` (timeout 30 с, как
Element; первый запрос - initial sync) и выполняет действия по весам:

| Действие | Запрос | Вес по умолчанию |
|---|---|---|
| `send` | `PUT /rooms/{id}/send/m.room.message` или `m.room.encrypted` (в шифрованной комнате, фиктивный шифротекст) | 40 |
| `typing` | `PUT /rooms/{id}/typing/{user}` | 15 |
| `receipt` | `POST /rooms/{id}/receipt/m.read/{event}` на последнее событие из /sync | 15 |
| `messages` | `GET /rooms/{id}/messages?dir=b` от `prev_batch` из /sync | 6 |
| `keys_query` | `POST /keys/query` по участникам комнаты (до 20) | 6 |
| `keys_upload` | `POST /keys/upload`, 5 новых OTK | 2 |
| `media_upload` | `POST /_matrix/media/v3/upload`, `media_kb` ±50% | 3 |
| `media_download` | `GET /_matrix/client/v1/media/download/...` (аутентифицированное) | 6 |
| `create_room` | `POST /createRoom` (private_chat) с двумя приглашенными | 1 |
| `join_leave` | вход в комнату профиля или выход, если комнат больше `rooms_per_user` | 3 |
| `invite` | `POST /rooms/{id}/invite` случайного пользователя | 3 |

Приглашенный принимает приглашение из своего /sync (`join_invite`). 429 у действия -
пауза пользователя на `retry_after_ms`.

Модели нагрузки:

- `mode: users` (по умолчанию) - закрытая: все пользователи активны, пауза между действиями
  (think time) экспоненциальная со средним `think_time`; частота действий ≈ `users / think_time`.
- `mode: rps` - открытая: `target_rps` действий в секунду суммарно, случайным активным
  пользователям, независимо от скорости ответов; сверх `max_inflight` одновременных действие
  пропускается (`rps_dropped_inflight` в отчете) - генератор не копит очередь.

Время прогона: `ramp` - пользователи подключаются равномерно (initial sync не приходит пачкой),
частота в `mode rps` растет линейно; `warmup` - от старта до начала замера (включает ramp);
`duration` - окно замера; `drain` - действия остановлены, /sync еще ждет доставки
отправленного в окне.

## 3. Метрики

**Доставка** (главная): от ответа на `PUT /send` у отправителя до появления события в /sync
каждого получателя - отдельный замер на получателя (p50/p95/p99/max). Сообщение метится полем
`io.syngo.loadgen` в content (id прогона и момент начала PUT в микросекундах; наносекунды не
влезают в диапазон целых canonical JSON). Получатели - участники комнаты с уже выполненным
initial sync на момент ответа; полнота = доставлено / ожидалось. Событие, пришедшее
получателю раньше ответа отправителю, считается с задержкой 0 (`before_ack`). Дополнительно -
задержка от начала PUT (включает запись события).

**Эндпоинты** (сторона клиента): p50/p95/p99/max, RPS, коды ответов, 429, сетевые ошибки
(`net`). `sync_longpoll` - время long-poll (ожидание событий), а не работа сервера; работа
/sync без ожидания - в разделе сервера (`syngo_sync_duration_seconds`).

**Сервер** (`-metrics-url`, ops-листенер syngod `/metrics`): разности за окно -
`syngo_http_requests_total` и квантили `syngo_http_request_duration_seconds` по маршрутам,
/sync без long-poll, 429, ожидание пула БД (`syngo_db_pool_empty_acquires_total`), GC, ряд
long-poll и горутин. У Synapse - `synapse_http_server_*` по сервлетам.

**Процесс** (`-server-pid`): RSS и CPU из `/proc/<pid>` (среднее за окно и пик по ряду с шагом
`-sample-interval`).

**PostgreSQL** (`-pg-dsn`): разности `pg_stat_database` (TPS, cache hit, tup_*, temp, deadlocks),
ряд соединений базы, топ-15 запросов `pg_stat_statements` по суммарному времени. Расширению
нужен `shared_preload_libraries=pg_stat_statements` и `CREATE EXTENSION`; без них в отчете
причина, остальное снимается. Если на кластере бенч-базы расширение не загружено, топа
запросов в отчете нет; у Synapse-стенда своя PostgreSQL с ним.

## 4. Профили

| | S (smoke) | M | L |
|---|---|---|---|
| Пользователи | 50 | 500 | 5000 |
| Комнаты / на пользователя | 20 / 5 | 200 / 10 | 1000 / 15 |
| Шифрованных комнат | 30% | 30% | 30% |
| Think time | 5 с | 5 с | 10 с |
| Действий в секунду (≈) | 10 | 100 | 500 |
| Из них send | ≈4/с | ≈40/с | ≈200/с |
| Ramp / warmup / замер / drain | 15 с / 20 с / 60 с / 10 с | 60 с / 90 с / 10 мин / 15 с | 5 мин / 6 мин / 30 мин / 30 с |
| Параллельность подготовки | 8 | 16 | 32 |

Частота отправки у одного пользователя ≈ 0,4 / think time (0,08/с для S и M) - ниже
прод-лимита `rate_limit.send` (0,2/с, burst 10): 429 на send под профилем - сигнал, а не
свойство профиля. На L генератору нужно ~10 тыс. соединений (long-poll + действие на
пользователя): `ulimit -n` и `net.ipv4.ip_local_port_range` на машине генератора.

Свой профиль - JSON поверх встроенного (`base`), неизвестные поля - ошибка:

```json
{"base": "M", "users": 1000, "duration": "20m", "mode": "rps", "target_rps": 300,
 "weights": {"send": 60, "typing": 20, "receipt": 20}}
```

`weights` в JSON заменяют встроенные целиком. Флаги `-users -rooms -rooms-per-user -duration
-warmup -ramp -think -rps -mode -seed` переопределяют поля профиля.

## 5. Стенд

`scripts/load-stand.sh up` собирает syngod из текущего checkout в `var/loadstand/`, применяет
миграции к бенч-базе и запускает процесс:

| Параметр | Значение | Переменная |
|---|---|---|
| Клиентский API | `127.0.0.1:38008` | `LOAD_ADDR` |
| ops (`/metrics`, `/health/ready`) | `127.0.0.1:39108` | `LOAD_OPS_ADDR` |
| База | `postgres://syngo:syngo@127.0.0.1:5432/syngo_bench` (имя обязано содержать `bench`/`perf`) | `LOAD_DSN` |
| Лимиты | `prod` / `off` | `LOAD_RATE_LIMIT` |
| `database.max_conns` | 10 (как в проде) | `LOAD_DB_MAX_CONNS` |
| Лог | `info`, json, `var/loadstand/syngod.log` | `LOAD_LOG_LEVEL` |

Конфиг - по `deploy/prod/config.yaml`: `env: prod`, таймауты, федерация выключена, закрытая
регистрация, медиа локально. Секреты (`sync.token_secret`, `registration_shared_secret`)
генерируются один раз в `var/loadstand/secrets.env` (0600).

`LOAD_RATE_LIMIT=prod`: `send` (0,2/с, burst 10), `media_upload` (10/с, 50), `sync` (2/с, 20 на
устройство) - как `config.Default`, то есть как в проде; `login_*` и `register_ip` сняты - ими
пользуется только подготовка пула (у прода 0,003/с на IP: 5000 пользователей готовились бы
сутки). `off` - сняты все. Режим попадает в отчет (`rate_limit`). Лимит /sync у syngod
задерживает long-poll, а не отклоняет его: в комнатах с частыми событиями он добавляет
задержку доставки; у Synapse лимита на /sync нет - при сравнении учитывать (или `off`).

Уже занятый порт скрипт не берет (проверка через `ss`). `down` останавливает процесс, `reset` (только остановленного)
очищает схему базы, медиа и кеш токенов.

## 6. Запуск

```sh
make load-smoke                      # поднять стенд (если не поднят), профиль S, остановить
make load-stand-up                   # стенд отдельно (для серии прогонов)
make load PROFILE=M                  # профиль M на поднятом стенде
make load PROFILE=M LOAD_ARGS="-duration 5m -users 300"
make load PROFILE=bench/my.json      # свой профиль
make load-stand-down
```

`scripts/load-run.sh` берет адреса, PID, DSN и секрет из `var/loadstand/stand.env` и
передает генератору `-label` с конфигом стенда. Напрямую:

```sh
LOADGEN_SHARED_SECRET=... LOADGEN_PG_DSN=... go run ./cmd/loadgen \
  -target http://host:8008 -metrics-url http://host:9108/metrics -server-pid 1234 \
  -profile M -label rate_limit=prod -out-dir var/loadtest
```

Код выхода: 0 - прогон прошел, 2 - не пройден гейт (доля ошибок без 429 > `-max-error-rate`
0,01 или полнота доставки < `-min-delivery` 0,99), 1 - сбой прогона. SLO-ориентиры влияют на
код только с `-strict-slo`.

Генератор и сервер на одной машине делят CPU: на M и L генератор выносить на отдельный хост
(или хотя бы смотреть CPU генератора). Тяжелые прогоны (M, L) - не на общем хосте.

## 7. Сравнение с Synapse

```sh
make load-synapse-up                 # Synapse 1.165.0 + своя PostgreSQL (docker)
make load-synapse PROFILE=S
make load-synapse-down               # scripts/load-synapse.sh reset - вместе с томами
```

| Параметр | Значение |
|---|---|
| Образ | `matrixdotorg/synapse:v1.165.0` (как у интероп-стенда), монолит без воркеров |
| Клиентский API / метрики / PostgreSQL | `127.0.0.1:38018` / `127.0.0.1:39118` / `127.0.0.1:35432` |
| PostgreSQL | 17, локаль C, `pg_stat_statements`, `cp_max` 10 (как `max_conns` syngod) |
| Лимиты (`LOAD_RATE_LIMIT=prod`) | по умолчанию Synapse, сняты `rc_login`, `rc_registration`, `rc_joins` (подготовка; у syngod лимита на join нет) |
| Регистрация | `registration_shared_secret` - тот же путь, что у syngod |

Генератор проверен с этим Synapse на малом профиле: регистрация, все действия, медиа v1,
`m.room.encrypted`, метрики `synapse_http_server_*` и `pg_stat_statements` работают.
После первого старта Synapse несколько минут выполняет background updates (`CREATE INDEX
CONCURRENTLY` видны в топе `pg_stat_statements`) - сравнительные прогоны делать после них.
Против чужого Synapse: `-target`, `-register shared-secret|login`, `-user-prefix`,
`-metrics-url` (если `enable_metrics`), `-pg-dsn`.

## 8. Как читать отчет

`report.md` - сводка, `report.json` - все данные (ряд `samples`, коды по эндпоинтам,
эндпоинты подготовки `setup_endpoints`).

- **Проверки** в конце: гейты (ошибки, полнота доставки) и SLO-ориентиры.
- **Доставка** растет раньше латентности send - первый признак насыщения (очередь пробуждений
  long-poll, лимит /sync, медленная сборка /sync).
- **Итог окна**: действий/с ниже профиля - сервер не успевает (закрытая модель замедляется
  вместе с ним); `rps_dropped_inflight` > 0 - то же в открытой модели.
- **Сервер**: `db_pool_empty_acquires` растет - пул мал (`LOAD_DB_MAX_CONNS`); /sync без
  long-poll p99 сравнивать с SLO ADR-0005 (incremental p99 ≤ 150 мс).
- **Процесс**: CPU около 100% × ядра или RSS растет весь прогон - предел или утечка.
- **PostgreSQL**: TPS / запросов клиента - сколько транзакций на запрос; топ
  `pg_stat_statements` - что оптимизировать первым.
- `sync_limited_timelines` - получатель пропустил события (timeline обрезан лимитом 20):
  полнота доставки занижена не по вине сервера, нужен больший `timeline_limit`.

## 9. Критерии (предложение)

Ориентиры для обсуждения, не утвержденные SLO; в отчете помечены «SLO (предложение)».

| Критерий | Порог | Профиль |
|---|---|---|
| Доставка, от ответа PUT, p95 | < 1 с | M |
| Доставка, p99 | < 2 с | M |
| `PUT /send` p95 | < 500 мс | M |
| Ошибки без 429 | < 1% (гейт) | все |
| Полнота доставки | ≥ 99% (гейт) | все |
| /sync без long-poll, p99 | ≤ 150 мс (ADR-0005) | M |
| 429 на send при прод-лимитах | 0 | S, M |

L - предел, а не критерий: найти частоту действий, при которой p95 доставки пересекает 1 с.

## 10. Smoke 21.11.2026

Профиль S, общий хост (Xeon E5-2620 v4, 8 CPU, load1 9-12 от соседних
стендов - цифры шумные), `LOAD_RATE_LIMIT=prod`. 50 пользователей, 8,8 действий/с, 100
запросов/с (из них ~91/с - возвраты long-poll /sync), 0 ошибок и 0 429.

| | `max_conns` 10 (прод) | `max_conns` 30 |
|---|---|---|
| Доставка p50 / p95 / p99, мс | 198 / 627 / 3369 | 225 / 652 / 879 |
| `PUT /send` p95 (text / encrypted), мс | 6181 / 4916 | 870 / 1197 |
| /sync без long-poll p50 / p95 / p99, мс | 116 / 1335 / 4675 | 44 / 528 / 965 |
| Выдач соединения с ожиданием / суммарное ожидание | 45084 / 749 с | 11799 / 50 с |
| CPU syngod (среднее за окно) | 41% ядра | 52% ядра |
| TPS PostgreSQL | 1192 | 1350 |

Уже на S узкое место - пул соединений БД (10 в проде): за 60 с запросы суммарно ждали
соединение 749 с, send p95 - 5-6 с, CPU процесса при этом < 1 ядра. ~12 транзакций PostgreSQL на
клиентский запрос, основная доля - сборки /sync: в комнате на 40 участников каждое событие
(сообщение, typing, receipt) будит long-poll всех участников. Пул 30 снимает основную очередь;
оставшееся время send (p50 ~200 мс) - запись события под нагрузкой /sync. Кандидаты в
отдельные задачи: число SQL на пробуждение /sync и размер пула по умолчанию.

## 11. Ограничения

- Членство считает генератор (по своим join/leave и /sync); в редких гонках (выход во время
  отправки) ожидаемое число получателей неточно на единицы.
- Шифрование фиктивное: сервер не расшифровывает, но to-device (обмен ключами Megolm) не
  генерируется - нагрузка E2EE занижена на `sendToDevice` и `/keys/claim`.
- Presence выключен фильтром (как у Element при выключенном presence на сервере).
- Один процесс генератора; на L желательно несколько машин - результаты не сливаются
  автоматически.
