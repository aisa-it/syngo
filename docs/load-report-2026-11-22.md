# Нагрузочное и стрессовое тестирование, оптимизация, сравнение с Synapse (22.11.2026)

Инструмент - `cmd/loadgen`, порядок запуска - [load-testing.md](load-testing.md).
Исходные отчеты прогонов - `bench/load-2026-11-22/`.

## Условия

| Параметр | Значение |
|---|---|
| Железо | Intel Xeon E5-2620 v4, 8 ядер, 64 ГБ, общий диск LVM (медленный fsync); хост общий |
| PostgreSQL | 17.12 в docker, отдельный экземпляр на каждый сервер, одинаковые настройки (`pg_stat_statements`, `max_connections=200`, остальное по умолчанию) |
| syngod | `scripts/load-stand.sh`, конфиг как в проде, лимиты частоты сняты (`LOAD_RATE_LIMIT=off`), пул 10 (исходно) / 20 (итог) |
| Synapse | 1.165.0, `scripts/load-synapse.sh`, один процесс без воркеров, лимиты `rc_*` сняты |
| Генератор | на том же хосте; профили S (50 пользователей, 20 комнат) и M (500 пользователей, 200 комнат, крупнейшая комната 449 участников), 30% шифрованных комнат, long-poll /sync как у Element |
| Модели | закрытая (think time 5 с, цель 10 действий/с для S и 100 для M); стресс - открытая модель ступенями по 2 мин (`scripts/load-stress.sh`) до отказа (ошибки > 5% или доставка < 95%) |

Главная метрика - задержка доставки: от ответа на `PUT /send` отправителю до появления события в `/sync` каждого получателя.
Генератор, сервер и PostgreSQL делят 8 ядер: под профилем M load1 поднимается до 15-22 от самого прогона, абсолютные цифры M занижены относительно отдельного сервера.

## Найденные узкие места и исправления

| # | Проблема (как найдена) | Исправление |
|---|---|---|
| 1 | Глобальная блокировка разбора push-действий: ~800 из 2285 горутин ждали `CatchUp` - отправка и каждый /sync синхронно ждали последовательного догона (дамп горутин) | Фоновый разбор порциями, отправка только сигналит, /sync ждет не дольше 200 мс без соединения |
| 2 | Запись на каждый запрос: `UPDATE access_tokens SET last_validated_at` и `UPDATE media SET last_accessed_at` - отдельный коммит с fsync на каждый запрос, все соединения в `WALWrite/WalSync` (`pg_stat_activity`) | Отметки активности копятся в памяти и пишутся пачкой раз в 10 с (как `client_ips` Synapse) |
| 3 | Пересчет счетчиков непрочитанного на каждую сборку /sync (`count(*) ... GROUP BY`, 14,5 мс) и удаление строк по receipt (49 мс) (`pg_stat_statements`) | Сводка `event_push_summary` (как в Synapse), receipt - один UPDATE, чистка прочитанного в фоне |
| 4 | Изменения состояния в /sync читали все state-события комнат пользователя в generic-плане; сводка большой комнаты (`array_agg` по 450 участникам) считалась на каждое сообщение; пул 10 мал | Частичный индекс state-событий, summary только при смене членства, пул 20 по умолчанию, очередь записи комнаты в памяти |
| 5 | `createRoom` с повтором пользователя в `invite` - 500 (генератор) | Повторы убираются |

Не влито: предел одновременных сборок /sync с адресными пробуждениями и «без пустых ответов» - в трех итерациях давал регрессию доставки на профиле M (99,7% -> 49-77%): пробуждения порождали больше пересборок, чем экономили, а сборки стояли в очереди слотов.

Профиль S, закрытая модель (цель 10 действий/с):

| | syngod (итог) | Synapse 1.165 |
|---|---|---|

| Ошибки | **0** | 0,5% |
| Доставка p50 / p95 / p99 | **188 / 328 / 405 мс** | 3,6 / 6,9 / 8,6 с |

| Первичный /sync p50 | < 1 с | 43,9 с |
| RSS процесса | **60 МБ** | 323 МБ |

| Действий/с | syngod: доставка, p95 | Synapse: доставка, p95 |
|---|---|---|
| 5 | - | 100%, 9,4 с (ошибки 1,3%) |

| 120 | 99,9%, 1,13 с | - |

Профиль M: Synapse без воркеров не выдерживает уже 10 действий/с - 910 из 918 первичных /sync 500 пользователей заканчиваются таймаутом, доставки нет; syngod держит 40 действий/с с доставкой p95 4,4 с и около 70 действий/с на пределе.

Итог: на одинаковом железе syngod обрабатывает на профиле S не меньше чем в 10 раз больше действий при задержке доставки и отправки в 20-80 раз ниже и потребляет в 5 раз меньше памяти; на профиле M Synapse в однопроцессной конфигурации не работает.

## Оговорки

- Synapse запущен одним процессом без воркеров (так в его стандартной установке). Для нагрузки уровня M Synapse рекомендует воркеры (синхронизатор, отправка событий, федерация) - с ними его цифры будут выше; сравнение с воркерами не проводилось.
- Хост общий, генератор на той же машине; fsync диска медленный - одинаково для обоих серверов.
- Один прогон на точку (кроме контрольных повторов) - разброс между повторами профиля M около 10-20%.
